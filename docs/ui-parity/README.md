# UI parity: making the app look exactly like the web

The Flutter app has to reproduce the approved web design, not reinterpret it. This
folder is how we keep that honest.

## The method, and why it is a generator

The web UI's real values live in 7,319 lines of hand-written CSS plus Tailwind
utilities spread across 104 Blade views. Two problems with writing a spec by hand:
it would be wrong somewhere in a body of work that large, and it would be stale the
next time the web UI changed.

So the spec is **derived**. Run the extractors and the documents follow:

```bash
php tools/ui-parity/extract.php          # app.css + 8 views' <style> blocks + the build
php tools/ui-parity/screen-map.php       # reads Laravel's own route table
php tools/ui-parity/reference-page.php   # reads the JSON the first two write
php tools/ui-parity/icons.php            # every inline <svg> → icons/*.svg, icons.json, cn_icons.dart
```

And to check a screen against a real phone rather than against its class names:

```bash
node tools/ui-parity/shoot.mjs http://localhost/camerooncommunity/public/login --device=se --height=553
```

It renders at a true iPhone viewport over the DevTools protocol and reports every scrolling
element, including content that can never be scrolled to. `--geo=lat,lng` fakes a location
fix, and `--eval` adds your own measurement. Plain `chrome --headless --window-size=375,...`
is not a substitute: on Windows it lays the page out at about 500px and crops it.

`app.css` is not the whole stylesheet, which pass 4 found the hard way: **eight views ship
their own `<style>` blocks**, 509 lines between them, holding the notification badge, the
connection toast, the Discover modal and 12 of the product's 38 keyframe sets. The extractor
reads those too. It also resolves the 18 avatar gradients out of
`public/build/assets/app-*.css`, because Tailwind v4 keeps its palette in OKLCH and the
values only exist resolved after a build.

Re-run both after changing the web UI. Nothing in this folder should be edited by
hand except this README.

## The one thing that is easy to get wrong

Inside the signed-in shell (`body.cn-app`) on a screen under 768px, **every font size
is 1.25× the desktop value.** The public landing page is excluded, and spacing and
fixed heights are deliberately not scaled, so the override enlarges text rather than
zooming the interface.

A naive reading of `text-sm` gives 14px where a phone actually renders 17.5px — build
from the documented Tailwind sizes and the whole app comes out a quarter too small.

Every number in this folder is already the phone value. The source of that rule is the
`MOBILE TEXT SCALE` block at the end of `resources/css/app.css`, which was generated by
a script (`textscale.py`) that no longer exists in the repo — the block itself is now
the only record, which is part of why it is parsed rather than trusted to memory.

## Scope

Decided on 2026-11-02:

- **Mirror the mobile web rendering** (under 768px) exactly. Tablet and desktop blocks
  in the stylesheet are skipped by the extractor on purpose.
- **Native only where the web has no answer** — iOS scroll physics, edge swipe-back,
  keyboard insets, the system share sheet, haptics on long-press. Everything the web
  does define, the app copies.
- **iPhone only** for the first release.

### There is no bottom navigation bar

Worth stating because an earlier version of this list promised one, and because a
comment in `app.css` still says "Leave room for the mobile bottom nav (h-14 = 3.5rem)"
immediately before setting `bottom: 0`. Nothing in the codebase renders one. Navigation
on a phone is the header's six-tab row plus the drawer behind the ☰. **The app must not
add a bottom bar** — it would be the single most visible way to look unlike the web.
